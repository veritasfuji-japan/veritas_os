## 1. Purpose

This is the first audit-only step after Architecture Freeze.

It does **not** delete, merge, rename, or rewrite broad implementation. Its job is
to separate:

- frozen proven-path code;
- active non-core code;
- duplicate candidates;
- dead-code candidates;
- compatibility candidates; and
- uncertain code that must not be deleted without more evidence.

The governing rule for this phase is:

> **Audit before deletion. Uncertain means preserve.**

## 3. Initial evidence-backed findings

### F-001 — Frozen controlled Execution Proof core

**Classification:** `FROZEN_CORE`  
**Confidence:** HIGH

The Architecture Freeze manifest, dedicated Decision-to-Effect workflow and proof
test define a protected baseline. Consolidation must preserve the proven semantics:

- Authorization issuance is not execution permission.
- Consumption is single-use.
- Current governance is rechecked before effect.
- Dispatch intent is durable before transport.
- `EFFECT_UNKNOWN` is uncertainty, not failure.
- Lookup absence does not prove no effect.
- Blind redispatch is prohibited.
- Replacement business-event execution stays blocked while unresolved/confirmed.
- Reconciliation is read-only.
- Receipt/Outcome are retrospective evidence.
- Crash recovery never resends the effect.
- Decision → authorization → effect → receipt/outcome lineage remains verifiable.

**Action:** compute the transitive dependency closure of this frozen path before
removing anything that it imports indirectly.

### F-003 — Legacy policy-manifest SHA-256 verifier

**Classification:** `COMPATIBILITY_CANDIDATE`  
**Confidence:** MEDIUM

Candidate:

`veritas_os/policy/signing.py::verify_manifest_sha256`

Its own docstring describes it as a legacy SHA-256 integrity check. Initial code
search found direct tests and historical review documentation, but no supported
runtime caller.

That is not enough evidence to delete it because runtime import indirection,
packaging, CLI entry points or migration tooling may still consume it.

**Action:** confirm symbol-level runtime/CLI/entry-point reachability. If zero
supported consumers remain, remove or deprecate it in a narrow follow-up PR.

### F-004 — TrustLog verifier surface cluster

**Classification:** `UNCERTAIN`  
**Confidence:** HIGH

Initial path inventory finds **31 Python files / 495,393 bytes** with
`trustlog` or `trust_log` in their path.

Important active verifier surfaces include:

- `veritas_os/logging/trust_log.py::verify_trust_log`
- `veritas_os/audit/trustlog_verify.py::verify_trustlogs`
- `veritas_os/scripts/verify_trust_log.py::verify_entries`

Initial search also finds active runtime, CLI and test consumers for the first two.

This is exactly where a superficial "duplicate verifier" cleanup would be risky:
the implementations may serve different ledgers, compatibility contracts and CLI
roles.

**Action:** create a role matrix covering ledger type, input contract, output
contract, consumers, cryptographic responsibility and compatibility behavior
before proposing any unification.

### F-006 — Oversized API schema module

**Classification:** `UNCERTAIN`  
**Confidence:** MEDIUM

`veritas_os/api/schemas.py` is **78,331 bytes**, placing it among the largest
runtime Python modules.

It is also connected to API tests and the actual `/v1/decide` surface used by the
frozen Decision-to-Effect proof, so size alone is not a reason to split it.

**Action:** map every schema class to route/client/test consumers. A later
mechanical split may be reasonable, but only if compatibility imports and public
API behavior are proven stable.

### F-007 — Coverage-oriented test sprawl

**Classification:** `DUPLICATE_CANDIDATE`  
**Confidence:** LOW

The repository currently has **471 Python test files versus 432 runtime Python
files**. This is not inherently bad, but several coverage/ext suites are very large:

- `test_pipeline_stages_ext.py` — 277,589 bytes
- `test_server_api.py` — 182,859 bytes
- `test_fuji_gate.py` — 131,189 bytes
- `test_kernel_decide_ext.py` — 129,743 bytes
- `test_coverage_consolidated_ext.py` — 117,478 bytes

Large coverage suites frequently accumulate copied fixture setup and narrow
branch tests. That creates maintenance cost even when every individual assertion
is valid.

**Action:** use AST/test-name/target-function grouping to identify fixture and
assertion overlap. Preserve tests that defend distinct trust or safety boundaries.

## 4. What is *not* concluded yet

This initial inventory does **not** claim that:

- the parallel dry-run families are duplicates;
- TrustLog verifiers should be unified;
- `api/schemas.py` should be split;
- the plan8–plan17 test files can simply be deleted;
- any legacy-looking v1 module is unused; or
- test volume should be reduced to an arbitrary target.

Those conclusions require more evidence.

## 5. Follow-up audit order

Recommended sequence:

1. compute frozen-core transitive dependency closure;
2. generate inbound-import + test/doc reference counts for candidate modules;
3. build TrustLog verifier role matrix;
4. build plan8–plan17 target-function/test-case matrix;
5. verify all consumers of `verify_manifest_sha256`;
6. map canonical-promotion vs live-adapter dry-run responsibilities;
7. rank narrow follow-up PRs by confidence and blast radius.

Only after these steps should broad consolidation begin.

## 6. Follow-up PR strategy

Preferred order after audit evidence is complete:

1. high-confidence dead code;
2. exact duplicate test fixtures/helpers;
3. compatibility code with verified zero supported consumers;
4. canonical duplicate verifier/helper implementations;
5. larger abstraction/schema simplification.

Every follow-up that touches the frozen proof path must rerun the dedicated
`reproducible-decision-to-effect-e2e` check.

## 7. Exit condition for TASK-010

TASK-010 is complete only when the inventory is strong enough to justify the
removal/refactor sequence without guessing.

This first PR is therefore an **audit foundation**, not the consolidation itself.
